# Prepare and review a release

Read the project's release configuration and installed `docs/release/README.md`. Run `python3 scripts/release_prepare.py --repo . --json` from the project root; consult `--help` for requested version or target parameters. If the tool/package/configuration is absent, report what is needed instead of choosing or installing a release policy.

Keep `none`, `commit-sha` and `semver-tag` distinct. Ordinary pushes do not require tags. A same-name tag pointing elsewhere is a blocker; never move or delete it. Bind results to the exact source commit and repeat preparation after target or configuration drift. Preparation accepts existing annotated tags that peel to the same commit; execution refuses them because it requires exact raw object identity and creates only lightweight tags.

For execution planning or real publishing, read `docs/release/EXECUTION.md`. Local `python3 scripts/release_execute.py status` returns `executionAvailable: false`; this describes the local entrypoint, while real GitHub providers require a configured trusted host. Use `plan --repo . --preparation PATH` for a saved preparation; provide `--remote`, `--release-spec` or `--output` only for the user's intended target and output. Write notes, specs and local records only when requested.

Draft notes from the agreed scope and verified changes. Report merged code, CI, artifacts, tag, Release, deployment and live verification separately. Preserve each component's exact source and artifact identity, including unchanged components; distinguish local builds from CI artifacts. Missing facts stay unknown.

When a trusted host is already configured and the user requested real execution, help prepare its review bundle and, within the user's scope, dispatch the pinned workflow. Show the exact target repository ID, commit, raw tag, operations, Release content, expiry and bundle hash. The host must run pinned trusted code separately from candidate project data, verify signed OIDC and actual protected-environment review, and atomically consume each operation in a ledger outside the target project. The required human approval comment is `dev-workflow approve <bundle hash>`. A single-user host may explicitly permit self-review in trusted policy; a real approval record under the configured reviewer account is still required. General task intent in this chat does not establish that record. If the user explicitly authorizes registering the exact reviewed run, bundle hash, repository, version and operation set through their verified GitHub account, register only that scope and preserve the direct authorization evidence; record the method as delegated, never as an independent manual review or a claimed UI click. If the host, policy, credential access or human review is absent, retain the preparation result and report the specific blocker.

The local CLI `execute` refuses before repository reads, network access or mutation. Do not manufacture human approvals, grants, approval JSON, OIDC tokens or ledger entries; load candidate provider files; or use direct Git/gh/HTTP, environment or TTY fallbacks to bypass a refusal. Possession of an available token alone never authorizes posting reviewer approval; follow the exact delegated-registration condition above and any explicit user instructions. Real execution belongs to the authenticated host; this skill does not directly create local/remote tags or Releases, publish artifacts, deploy or change permissions. The remote commit must already exist: creating a tag through the host does not authorize branch push or object upload.

Return per-operation observed results and remaining gaps. Never automatically retry a mutation with unknown outcome or delete ledger markers to restore a consumed grant. Preserve `outcome_unknown` until fresh read-only evidence resolves it. Distinguish mocked tests from actual independent test-repository execution; pending human approval is not a passed end-to-end release.
